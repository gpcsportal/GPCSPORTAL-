# GPCS Portal

Production Laravel 12 portal for Government Polytechnic College, Shivpuri.

## Included modules
- Student/Faculty registration, login, forgot-password and reset-password.
- Hidden Admin entry with protected dashboard, moderation, reports, activity logs and account settings.
- Paper upload with Subject Master metadata lookup and exact duplicate protection.
- Notes upload with five mandatory academic fields: Branch, Semester, Year, Subject Name and Subject Code. Attachment is optional.
- Gallery uploads and moderation.
- Intervention Image compression with fail-safe original retention.
- iLovePDF compression with fail-safe original retention.
- Contact form.

## Upload limits
- One Paper file: 100 MiB maximum.
- One Notes attachment: 200 MiB maximum.
- Gallery image: 20 MiB maximum by default.

## Admin first login
`AdminSeeder` does not ship a working password in source code. Before first seeding, set `ADMIN_IDENTIFIER`, `ADMIN_EMAIL`, and a strong temporary `ADMIN_PASSWORD` in Railway. A suitable setup identity can be `GPCS-ADMIN` and `admin@example.com`; the password must be unique and supplied only as an environment variable. After the first successful Admin login, immediately change the Admin ID/password from Admin → Account Settings and remove or rotate the temporary seeding password variable.

## Account recovery and email delivery
Forgot-password and reset-password use Laravel's password broker. Production email delivery requires a real outbound mail provider configured in Railway (`MAIL_HOST`, `MAIL_USERNAME`, `MAIL_PASSWORD`, `MAIL_FROM_ADDRESS` and related SMTP variables). The API keeps known and unknown email addresses indistinguishable and returns a temporary-service error instead of claiming success when the mail transport or broker cannot send.

Student and Faculty registration requires acceptance of the public Terms and Privacy pages. Email remains the required sign-in and password-recovery credential for both roles.

## Dependency lock
A genuine `composer.lock` generated by Composer is committed to the repository. Production and CI therefore install the same resolved dependency versions instead of resolving new package versions on every deployment. The lock is checked with `composer audit --locked` in CI.

## Code quality checks
`.github/workflows/code-quality.yml` runs on pull requests to `main` and pushes to `main`. It rejects tracked production environment/private-key files, validates Composer metadata, installs locked dependencies, runs the Composer security audit, checks PHP and JavaScript syntax, boots Laravel routes, runs migrations against an isolated SQLite database, and executes the full test suite.

`.github/dependabot.yml` checks Composer and GitHub Actions dependencies weekly so upgrades arrive as reviewable pull requests instead of silently changing production builds.

## Railway deployment
See `RAILWAY_DEPLOYMENT.md`. Production uses Railway Railpack auto-detection with the Laravel/FrankenPHP runtime. Legacy Procfile/Nixpacks overrides are intentionally not present because they could reintroduce a development-server start path.

## Admin bootstrap credentials
No working Admin password is hardcoded in source. `AdminSeeder` reads `ADMIN_IDENTIFIER`, `ADMIN_EMAIL`, and `ADMIN_PASSWORD` from environment. Example bootstrap placeholders are:

```text
ADMIN_IDENTIFIER=GPCS-ADMIN
ADMIN_EMAIL=admin@example.com
ADMIN_PASSWORD=<set-your-own-strong-temporary-password-12+-chars>
```

The ID/email are examples; the password must be your own strong temporary value. **Do not use a documented example password. Change the Admin ID/password immediately after the first successful login and rotate/remove bootstrap environment values.**

## Front-end build
No Node/Vite build is required for deployment. The approved portal UI is delivered by `resources/views/portal.blade.php` and the production integration bridge is `public/assets/gpcs-backend-bridge.js`.

## Persistent uploads
Attach a Railway Volume at `/app/storage/app/public` before relying on Paper, Notes or Gallery uploads. See `RAILWAY_DEPLOYMENT.md`.

`QA_REPORT.txt` is an older static verification snapshot. The GitHub Actions code-quality workflow is the current executable verification path for dependency, syntax, route, migration and test checks.


## Verification artifacts

`QA_REPORT.txt`, `PHP_LINT_REPORT.txt`, `JS_LINT_REPORT.txt`, `FILE_MANIFEST.txt`, `SHA256SUMS.txt`, and `STATIC_VERIFICATION.json` are historical packaging snapshots. They are retained for traceability, but the GitHub Actions workflow and the currently deployed Railway commit are the authoritative verification sources for the live portal.
